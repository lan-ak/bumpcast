- **Gate changes (free, in the app only, no push):**

### Rating prompt on the first forecast (free and Pro)

Sent Oct 30 by the "Free user app review prompt" session. It was already in `main`'s working tree, uncommitted, so no merge was needed. **Lanre, Oct 30: keep it in 1.0.3.** That includes asking users who update from 1.0.2, and asking before anyone has flown. It replaces the "after a matched landing only" rule in `1.1-BACKLOG.md`.
- **Why:**
  - Free users were never asked.
  - Adding a flight opens the forecast, and the first-forecast soft paywall (`first_grade_viewed`) comes up over it.
  - The old after-adding-a-flight prompt fired 2.5 s later, saw the paywall, and gave up without trying again.
- **What changed:**
  - **`Services/ReviewPrompt.swift`:**
    - New moment `firstForecast`, fired by `ReviewPrompt.forecastShown(_:)`. It counts advance or confirmed forecasts, not the global outlook, and asks once per install, 3 s after the forecast opens.
    - If a paywall is showing, it waits up to 10 min for it to close, then asks 1 s later. A guard stops a second open from asking twice.
    - The matched-landing moment stays at once per version and now also waits for paywalls. The after-adding-a-flight moment is removed.
  - **`Views/ForecastView.swift`:** `onAppear` calls `forecastShown`, next to `firstGradeViewed`.
  - **`Views/FlightsListView.swift`:** with no Superwall campaign on `flight_added`, the fallback now only asks for notifications.
  - **`SUPERWALL.md`:** the `flight_added` line is updated to match.
- **Worth knowing:**
  - **Existing users get asked too.** The `firstForecast` key is new, so everyone updating from 1.0.2 is asked on the first forecast they open in 1.0.3. That's probably intended.
  - **It's earlier than the old rule.** `1.1-BACKLOG.md` said to ask only after a landed flight where the forecast matched. This asks before anyone has flown with the forecast. Apple allows the system prompt at most 3 times a year, and this spends one early.
  - If the user leaves the forecast while a paywall is up, the prompt can appear on whatever screen they're on once it closes.
- **Release notes:** nothing to say. Only the prompt timing changes.
- **Checked** (release session, Oct 30):
  - The diff was read.
  - On the whole of `main`, 87/87 tests pass and the Release configuration builds.
  - **Simulator, fresh Debug install, free user (`-demo`):** opening the first forecast showed "Enjoying BumpCast?" after about 3 s. Reopening it after "Not Now" didn't ask again.
  - **Wait-for-the-paywall path (Oct 31, on SuperwallKit 4.18.3):** a fresh install online showed the flight paywall on the first forecast, with no rating sheet over it. Closing the paywall brought "Enjoying BumpCast?" about a second later.

### SuperwallKit 4.18.0 → 4.18.3

Sent Oct 31 by the "Superwall SDK update" session. It's in `main`'s working tree, uncommitted.
- **Files:**
  - `ios/project.yml`: SuperwallKit `from: 4.18.3`. It's the only tracked file that changed.
  - The generated project (gitignored) pins 4.18.3, rev `d2f2002e`. Superscript stays at 1.0.15.
- **What the new versions bring** (release notes, read by the release session):
  - **4.18.1:** a `device.simulatorModel` paywall variable, simulator only.
  - **4.18.2:** an `airbridgeId` integration attribute. We don't use Airbridge.
  - **4.18.3:**
    - The SDK's Core Data store moves from the root of Application Support into `com.superwall.database.Store/`, once, on first launch.
    - Entitlements no longer go inactive during an App Store billing grace period (StoreKit 2). That's good for us, because Pro is Superwall's status.
- **Does the move touch our files?** No. BumpCast's `LocalStore` keeps `snapshot.json`, `map.json` and `Demo/` in that same root. The release session read `V5Migrator` and `CoreDataStoreLocation` in 4.18.3: they move only Superwall's own `<model>.sqlite` file. If the move fails, the old store keeps being used and the move is retried on the next launch.
- **Checked:**

### Airport wind worker (makes the gusty labels real)

- **What:**
  - New `worker/src/smooth_worker/airfield.py`. Each poll makes one batched TAF request to aviationweather.gov for the airports of flights within 30 h, cached for 10 min.
  - An end counts as gusty at 25 kt or more within ±60 min of takeoff or landing, and stays gusty until gusts drop below 20. PROB groups are ignored.
  - If the feed fails, the last answer is kept only while its TAF still covers the window.
- **Tagging:** `cause` goes only on confirmed (GTG) climb or descent stretches peaking at or below field elevation + 4,000 ft. Never on the outlook, never on cruise. Numbers, grade and pushes are untouched, and a test proves a cause-only change adds no "what changed" line.
- **Shadow data:** `forecasts.airport_wind` (jsonb, default `[]`) holds the decision for each end, the exclusions, and the floor it would have used. It's never shown. `landing_reports.forecast_wind` is filled by the trigger.
- **Who sees it:** Pro users on 1.0.3, only on confirmed forecasts with real gusts. That's rare this week and more common in winter. 1.0.2 ignores the field.
- **Smoke test** (brainstorm session): 9 airports parsed in one request. SFO had 22 kt, under the threshold.
